Platform Overview

Three distinct API surfaces serving different consumers, all metered and billed per call.

Surface Base URL Auth Method Primary Consumers
Enterprise /api/enterprise/v1/ X-API-Key Third-party integrations, automation
Mobile App /api/v1/ Sanctum Bearer iOS / Android staff app
Web Frontend /api/web/v1/ Sanctum Bearer React SPA (browser)

Architecture

Multi-Tenancy
Each organisation has its own MySQL database. The API layer validates your key, identifies your organisation, and switches the active database connection per request.
Billing Pipeline
Every successful response triggers a usage event via QueueUsageEvent middleware. Fires after the response is sent (zero latency impact).
AI Caution Pipeline
Every shift checkout and shift note submission sends notes to Azure OpenAI GPT-5.4. Severity >= 5 triggers ShiftCaution records and care manager notifications.

Authentication

Three authentication methods across the three API surfaces.

Enterprise API — API Key

Every enterprise request must include your API key:

X-API-Key: impl_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Or as a Bearer token:

Authorization: Bearer impl_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
Key format: impl_live_<22-char-prefix><secret-suffix>. Keys are bcrypt-hashed at rest. The first 22 characters identify the key; the full value is validated on each request and cached for 5 minutes.
StatusBehaviour
activeRequests proceed normally
revokedReturns 401 Unauthorized
expiredReturns 401 Unauthorized

Mobile App — Sanctum Token

Staff authenticate via the login endpoint:

POST /api/v1/login
Content-Type: application/json

{ "email": "worker@example.com", "password": "..." }

Include the returned token on all subsequent requests:

Authorization: Bearer <sanctum-token>

Web Frontend — Sanctum (Cookie/Token)

The React SPA uses Laravel Sanctum's cookie-based session authentication. The token is stored in memory (not localStorage) and injected into requests by api.ts.

Usage Tracking

Every API call is tracked, calculated, and reported to Stripe for billing.

How It Works

  1. Reads bulk_item_count from request attributes (set by controllers on bulk endpoints)
  2. POSTs a usage event to the API management server at http://127.0.0.1:8083/api/internal/usage-event
  3. API management server queues a ProcessUsageEvent job on the api-usage queue
  4. UnitCalculatorService::calculate() determines units based on endpoint, method, status code, and item count
  5. Event stored in api_usage_events with units, category, reason, duration_ms
  6. If units > 0, a SendStripeUsageEvent job reports to Stripe for billing

Usage Event Record

{
  "customer_id": 1,
  "endpoint": "/api/web/v1/scheduler/publish",
  "method": "POST",
  "status_code": 200,
  "units": 50,
  "weight_category": "bulk",
  "duration_ms": 142,
  "metadata": {
    "ip": "203.0.113.5",
    "user_agent": "Mozilla/5.0 ...",
    "bulk_item_count": 50,
    "endpoint_category": "scheduler",
    "reason": "bulk_per_item"
  }
}

Bulk Operations Guide

Optimise your API usage with intelligent batching strategies.

General Rules

  • All bulk endpoints accept up to 500 items per call
  • Billing is max(min_units, item_count) — you always pay at least the minimum
  • HTTP 201 if all items succeed, 207 Multi-Status if any fail
  • Failed items return errors per index — you can retry only the failed items
  • Errors on individual items do not roll back successful items

Cost-Optimisation Tips

  1. Batch intelligently — one call with 50 items at 50 units is the same as two calls with 25 items each (2 x 25 = 50 units). Batching saves nothing on units but saves on latency and rate limit headroom.
  2. The minimum floor matters for small batches — publishing 1 shift still costs 25 units. Accumulate small batches where possible.
  3. Import is expensive per row — a 100-row import = 3,000 units ($22.50). Validate data client-side before importing.
  4. Errors are free — if your code does a GET first to check existence and it returns 404, that's free. Only pay on success.
  5. AI on checkout is unavoidable — every appointment/checkout triggers the AI pipeline (60 units) regardless of whether cautions are found.
